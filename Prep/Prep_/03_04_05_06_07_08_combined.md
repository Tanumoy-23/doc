# TOPIC 3: GIT PIPELINE & CICD FOR INTERVIEWS

## Core Concepts

**Pipeline Stages:**
1. **Trigger:** Push to repo, PR, schedule
2. **Build:** Compile, tests, create artifacts
3. **Scan:** Security, code quality
4. **Deploy staging:** Integration tests
5. **Deploy prod:** Blue-green, canary, rolling

## Interview Questions

**Q1: "Design a CI/CD pipeline for microservices"**

Answer outline:
- Trigger: Git push → GitHub Actions
- Build: Compile → Docker image → Push to registry
- Scan: SAST, container scan, dependencies
- Deploy staging: Pull image → Deploy to staging K8s
- Test: Integration tests, smoke tests
- Deploy prod: Blue-green to production
- Monitor: Metrics, logs, alerts

For multi-tenant:
- Build once, deploy to multiple tenant namespaces
- Configuration per tenant (via Helm values)
- Artifacts versioned per tenant

**Q2: "How would you handle failed deployments?"**

- Automated rollback if health checks fail
- Keep N previous versions
- Pod disruption budgets prevent all pods dying
- Slack/email alerts
- Manual rollback option

**Q3: "Design deployment strategy for database migrations"**

Answer:
- Zero-downtime migrations:
  1. Deploy new code (reads old + new schema)
  2. Run migration
  3. Deploy new code (reads only new schema)
  4. Rollback only steps 1 & 3 (not migration)

## Interview Questions

Flow:
1. User signs up → Keycloak creates user
2. Create tenant namespace in K8s
3. Create service account for tenant
4. Generate API key/JWT
5. Set ResourceQuota (limits)
6. Assign roles (what can tenant do)

**Q2: "How would you prevent tenant A from accessing tenant B's data?"**

- Namespace isolation (K8s API level)
- RBAC: RoleBinding restricts to own namespace
- NetworkPolicy: Pods can't reach other namespace
- Secret encryption: Even if someone gets etcd, can't read
- Audit logging: Track all access attempts
- PVC isolation: Storage separate

Features by tier:

Implementation:
- Keycloak custom claims (tier info)
- K8s ResourceQuota (enforce limits)

- Storage quota enforcement
- License expiry checks

# TOPIC 5: OBSERVABILITY (OpenSearch, DataPrepper, Fluent Bit, OTEL, Prometheus)

## Architecture

```
Applications
    ↓ (logs, metrics, traces)
Fluent Bit (collect)
    ↓
OpenSearch (logs) + Prometheus (metrics)
    ↓
Dashboards + Alerts
```

## Core Components

**Fluent Bit:**
- Lightweight log collector
- Ship logs to OpenSearch, S3, Datadog
- Filter/parse logs
- Multi-tenant: Add tenant ID to logs

**DataPrepper:**
- Transform logs
- Enrich with context
- Pipeline: input → processors → output

**OTEL Collector:**
- Collect metrics, traces, logs
- Exporters to Prometheus, Jaeger, etc.
- Agents on each pod

**OpenSearch:**
- Time-series DB for logs
- Query language (SQL-like)
- Indexing (daily, by tenant)
- Retention policies

**Prometheus:**
- Metrics (counter, gauge, histogram)
- Scrape-based
- For infrastructure (CPU, memory, requests)

## Interview Questions

**Q1: "Design observability for multi-tenant platform"**

```
Per-tenant:
1. Fluent Bit collects logs → adds tenant_id
2. DataPrepper enriches logs
3. OpenSearch stores (index per tenant for isolation)
4. Grafana dashboard (tenant can see only their logs)

Shared:
1. OTEL Collector gathers metrics (CPU, memory, network)
2. Prometheus stores metrics
3. Grafana shows platform health (all tenants)
```

Dashboards:
- Platform ops: Errors, latency, availability
- Finance: Cost per tenant
- Product: Usage metrics
- Tenant: Their own logs/metrics (RBAC controlled)

**Q2: "How would you troubleshoot high latency?"**

Tools:
- OpenSearch: Query logs for errors/timestamps
- Prometheus: Check CPU/memory spikes
- Traces: Use OTEL to see request flow
- Database slow query logs
- Network metrics (latency between services)

Drill-down:
1. Check if widespread or single tenant
2. Check service logs (OpenSearch)
3. Check infrastructure (Prometheus)
4. Check traces (if spans are slow)
5. Check database (slow queries)

**Q3: "How to track GenAI costs in observability?"**

Metrics:
- tokens_input_total (gauge)
- tokens_output_total (gauge)
- api_cost_total (counter)
- api_latency_seconds (histogram)

Logs:
- Who called API, when, cost
- Audit trail (compliance)

Dashboard:
- Cost per tenant
- Cost trends
- Cost per feature
- Budget vs actual

# TOPIC 6: HELM CHARTS FOR INTERVIEWS

## Core Concepts

**Helm:**
- Package manager for K8s
- Chart = package (templates + values)
- Release = instance of chart
- Values = configuration

**Chart structure:**
```
myapp-chart/
├── Chart.yaml (metadata)
├── values.yaml (defaults)
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── configmap.yaml
└── requirements.yaml (dependencies)
```

## Interview Questions

**Q1: "Design Helm chart for multi-tenant deployment"**

Chart structure:
```yaml
# values.yaml
tenant:
  name: customer-1
  namespace: tenant-customer-1
  replicas: 3
  resources:
    cpu: 2
    memory: 4Gi
  
database:
  enabled: true
  storage: 10Gi
```

Templates:
```yaml
# deployment.yaml
metadata:
  namespace: {{ .Values.tenant.namespace }}
  name: {{ .Values.tenant.name }}-app
spec:
  replicas: {{ .Values.tenant.replicas }}
  resources:
    limits:
      cpu: {{ .Values.tenant.resources.cpu }}
```

Deploy:
```bash
helm install tenant-1 ./chart -f values-tenant1.yaml
helm install tenant-2 ./chart -f values-tenant2.yaml
```

Each tenant gets separate release with own config.

**Q2: "How would you handle Helm upgrades safely?"**

- Test in staging first
- Use helm upgrade (not uninstall + install)
- Set history limit (keep previous releases)
- Use hooks for pre/post upgrade tasks
- Have rollback command ready: `helm rollback release`

**Q3: "Design Helm values structure for 100 customers"**

Approach:
- Base values.yaml (defaults)
- Per-tenant overrides (values-tenant-1.yaml)
- Environment overrides (prod.yaml, staging.yaml)
- Secret values separate (--values secrets.yaml)

# TOPIC 8: KAFKA & RABBITMQ FOR INTERVIEWS

## Kafka vs RabbitMQ

| Aspect | Kafka | RabbitMQ |
|--------|-------|----------|
| Model | Pub/Sub + Event log | Message queue |
| Persistence | All data on disk | Optional |
| Throughput | Very high (1M+/sec) | Moderate (50K/sec) |
| Replay | Can replay from offset | Consumed = gone |
| Ordering | Per partition | Per queue |
| Complexity | More complex | Simpler |
| Use case | Event streaming | Task queues |

## Interview Questions

**Q1: "When would you use Kafka vs RabbitMQ?"**

Use **Kafka** for:
- Event streaming (audit logs, metrics)
- Data pipelines
- Real-time analytics
- Replay requirement

Use **RabbitMQ** for:
- Simple messaging
- Task queues (background jobs)
- Simple pub/sub
- Lower complexity

For your platform:
- Kafka: Event log (who did what, when)
- RabbitMQ: Async tasks (send email, generate report)

**Q2: "Design a multi-tenant event streaming system"**

Per-tenant Kafka topic:
- topic: `tenant-1-events`
- topic: `tenant-2-events`
- Isolation (one tenant can't read other's)

Events:
- User login
- API call
- Cost incurred
- Feature used

Consumer groups:
- Analytics (processes events)
- Billing (calculates costs)
- Audit (compliance logging)

Retention:
- Keep 30 days (compliance)
- Compress (reduce size)

**Q3: "How to ensure exactly-once processing?"**

Challenge: Consumer crashes mid-processing.

Solutions:
1. **Idempotent processing:** Same message processed twice = same result
2. **Transactional writes:** Write offset + result together (atomic)
3. **Deduplication:** Track processed message IDs

Example:
```
Consumer reads message
Process it (may crash here)
Write result to DB + commit offset (same transaction)
If crashes: Offset not committed, retried
If same message processed twice: Idempotent logic handles it
```
